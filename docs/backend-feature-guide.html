What the new backend features actually do

This is a code-grounded tour of the Resume Builder’s new source-of-truth, job-tailoring, revision, and backup capabilities. It is written for someone who needs to use the API or extend the backend without accidentally weakening provenance or immutability.

The one mental model to keep

The backend has two lanes. The verified source lane is reusable, editable truth. The application lane is job-specific analysis and proposals. A generated revision is the immutable bridge between them.

1 · Source libraryProfile, content, bullets, skills and evidence.
2 · Base resumeSelect items and exact bullet IDs.
3 · ApplicationJob metadata, analysis, requirements.
4 · ProposalEvidence-grounded suggestions for review.
5 · RevisionCanonical snapshot plus optional PDF.
Safety boundary: analyzing a job or generating a proposal does not edit verified records. A user-approved proposal is revalidated against the current source fingerprint before it can produce a revision.

Source library: reusable truth

These features make source data easier to reuse, audit, and connect to job requirements.

Personal profiles

Typed personal-information records

PersonalInformation stores name, location, email, phone, LinkedIn, GitHub, website, summary, notes, and primary status. A BaseResume.personal_information_id points to the reusable record. Legacy layout_settings.contact remains readable and is backfilled once.

Routes: POST/GET /personal-information, GET/PATCH/DELETE /personal-information/{id}. Compatibility aliases use /personal-info.

Audit trail

Content and bullet history

ContentItemVersion and BulletVersion are append-only snapshots. Each create, edit, archive, and delete-related mutation records an action, version number, changed fields, and the prior data. History deliberately survives a later source-row removal.

Routes: GET /content-items/{id}/versions, GET /content-items/{id}/versions/{version}, and the equivalent bullet routes. /history is a compatibility alias.

Lifecycle

Archive, restore, duplicate

Archiving hides a content item without destroying it. Restore clears is_archived. Duplication creates a new source item and copies its bullets, while preserving independent identity so later edits do not leak back to the original.

Routes: GET /content-items/archived, POST /content-items/{id}/restore, POST /content-items/{id}/duplicate.

Canonical matching

Normalized skills and aliases

Skill is the canonical verified concept. SkillAlias stores globally unique normalized alternate names. ContentItemSkill explicitly relates a source item to a skill, avoiding fragile free-text-only matching.

Routes: POST/GET /skills, POST/DELETE /skills/{id}/aliases/{alias}, and POST/GET/DELETE /content-items/{id}/skills.

Applications: lifecycle and submissions

Richer job record

Application now supports source, location, employment type, salary range, contact name/email, deadline, notes, and applied/follow-up timestamps in addition to company, position, URL, description, status, and base-resume link.

Create and update with POST /applications and PATCH /applications/{id}; query with GET /applications and GET /applications/{id}.

Append-only status history

Status changes create ApplicationStatusHistory rows containing from-status, to-status, reason, and time. The current status remains on the application for fast filtering; the history is the audit trail.

Routes: POST /applications/{id}/status and GET /applications/{id}/status-history (with /history alias).

Submitted-revision tracking

Submission is tied to the exact generated Revision, not merely the current source data. The backend validates that the revision belongs to the application and is submittable, then stores submitted_revision_id and submitted_at. Retrying through an alias route preserves the same association.

POST /applications/42/submit
{
  "revision_id": 7,
  "submitted_at": "2026-09-09T15:30:00Z"
}

GET /applications/42/submitted-revision
// returns the immutable revision that was actually sent

Requirements, evidence, matching, and confirmation

This is the most connected feature group. Stable requirement IDs and explicit evidence links let model output stay explainable and let deterministic code make the final safety decisions.

Structured analysis

Durable job requirements

Analysis output accepts legacy strings and new typed objects, then normalizes each requirement by a case/whitespace-insensitive key. JobRequirement rows are application-scoped and retain stable integer IDs across re-analysis when the requirement is unchanged.

Each row has text, category (required, preferred, responsibility, technology, keyword, or other), priority, source text, and active state.

Evidence graph

Requirement evidence links

RequirementEvidenceLink points a requirement to a verified bullet, content item, or skill. Check constraints require a real source and one of the allowed source types. The API returns human context such as bullet text or skill name.

Routes: GET /applications/{id}/requirements, POST /applications/{id}/requirements/{requirement_id}/evidence, GET .../evidence, DELETE /requirement-evidence/{link_id}.

Deterministic service

Classifications and scoring

services/matching.py combines verified normalized skills, aliases, content-item relationships, selected base entries, bullet text, explicit evidence, and token overlap. It emits score, status, matched skills, evidence IDs, and human-readable signals. Base-resume evidence is stronger than library-only evidence; ambiguous aliases are not treated as proof.

Verified materialization

Confirmed missing information → source

A missing requirement can be confirmed first, then materialized as either a verified skill or a bullet in the shared source library. The ConfirmationMaterialization row records source type, source IDs, payload hash, source fingerprint, result fingerprint, and an idempotency key.

Routes: POST /applications/{id}/confirmations, POST /missing-confirmations/{id}/materialize, and application-scoped materialization aliases.

Revisions and semantic comparison

Every generated resume is stored as a JSON snapshot in Revision.resume_json, with a unique revision number per application. The snapshot is canonical: manual revision creation must match build_snapshot; a caller cannot smuggle arbitrary content into the immutable record.

Current sourceProfile + selected entries + bullets.
Canonical snapshotValidated contact, sections, entries, and provenance.
Revision rowImmutable numbered snapshot.
Rendered artifactsTeX and PDF under generated/.
CompareEphemeral semantic diff.

The comparison service compares entries, bullets, ordering, contact, skills, and provenance semantically rather than diffing raw JSON formatting. It reports added, removed, changed, and reordered records without persisting a redundant diff.

GET /applications/42/revisions/compare
    ?from_revision_id=7&to_revision_id=8

Backup and export

services/backup.py creates a versioned, self-contained ZIP containing a SQLite online-backup snapshot, generated artifacts, and a manifest with size and SHA-256 checksums. It stages and validates the archive before publishing it.

Safe creation

Uses SQLite’s online backup API, checks database and foreign-key integrity, rejects symlinks and paths outside the artifact root, and serializes version allocation for concurrent requests.

Safe restore

Validates member paths, format/schema, timestamps, limits, checksums, and SQLite integrity in a private staging directory. Only after validation does it replace live database/artifact content; failure restores the prior state.

API

POST /backups creates an archive. GET /backups lists validated backup metadata. The service layer also exposes restore/manifest operations for controlled local workflows.

Operational note: the backup includes generated PDFs/TeX as artifacts, but the authoritative data remains the database snapshot plus its integrity manifest. Treat the ZIP as a versioned local export, not as a public download.

Extension rules for future work

Preserve the lanes

Put reusable truth in source tables. Put job-specific assertions in application tables. Keep the boundary explicit with foreign keys, fingerprints, and provenance.

Prefer additive migrations

Existing JSON fields and route aliases support rolling upgrades. New durable concepts should get typed tables and stable IDs rather than another nested JSON convention.

Make retries safe

Use unique constraints and idempotency keys for materialization, backup versioning, and other side effects. A retry should return the same logical result or a clear conflict.

Test the negative path

Cross-application references, stale proposals, locked bullets, ambiguous aliases, unsafe archive paths, tampered backups, and invalid evidence are first-class behaviors, not edge cases.

Correctness and scalability

These issues are important after the critical/high risks are contained, especially as source and application history grows.

MEDIUMPATCH models are full-input models and may reset omitted fields

Resume and bullet PATCH routes accept models that behave like complete payloads. A caller that omits a field can unintentionally write its default, losing existing data. Use optional patch fields and apply only explicitly supplied values.

MEDIUMNullable ItemPatch fields can write NULL into required columns

Because nullable fields are accepted and then persisted, invalid updates can reach database constraints and surface as unhandled 500s. Validate required-field invariants at the API boundary and return a client-safe 422.

MEDIUMDuplicate resume entries can leak a database uniqueness error

The unique resume-entry constraint is correct, but the duplicate path is not translated into a stable conflict response. Catch the integrity error, roll back, and return a clear 409/422 that the UI can explain.

Remaining repair sequence

All critical and high-priority findings above are resolved. This order addresses the remaining correctness and maintainability work.

  1. Harden PATCH and conflict semantics. Use true partial-update schemas, validate required fields, and translate uniqueness/integrity failures into stable client errors.
  2. Complete frontend list scalability. Implement server-side pagination/search while preserving total and result state.
  3. Reduce query and migration coupling. Batch evidence/source reads, adopt versioned migrations, split the backend module by domain, and pin dependencies.
  4. Add regression coverage. Cover compiler timeout cleanup, fresh-clone startup, PATCH omission semantics, pagination/error states, and an end-to-end happy path.

Correctness and scalability

These issues are important after the critical/high risks are contained, especially as source and application history grows.

MEDIUMPATCH models are full-input models and may reset omitted fields

Resume and bullet PATCH routes accept models that behave like complete payloads. A caller that omits a field can unintentionally write its default, losing existing data. Use optional patch fields and apply only explicitly supplied values.

Recommended repair sequence

This order reduces user-visible correctness risk first, then makes the system easier to scale and maintain.

  1. Separate long-running work from the global barrier. Narrow SQLite/file locks, add bounded provider/render execution, and preserve run status on timeout/failure.
  2. Make application data freshness explicit. Version or invalidate analyses/proposals when job descriptions change; require current inputs at proposal and generation boundaries.
  3. Repair startup and local development paths. Handle a missing checkpoints directory and make npm run dev:backend select the project virtualenv/cwd consistently.
  4. Harden PATCH and conflict semantics. Use true partial-update schemas, validate required fields, and translate uniqueness/integrity failures into stable client errors.
  5. Fix frontend state handling. Centralize/disable duplicate actions, add idempotency keys, preserve load errors, and implement server-side pagination/search.
  6. Reduce query and migration coupling. Batch evidence/source reads, adopt versioned migrations, split the backend module by domain, and pin dependencies.
  7. Add regression coverage. Cover stale-analysis invalidation, timeout cleanup, fresh-clone startup, PATCH omission semantics, pagination/error states, and an end-to-end happy path.
